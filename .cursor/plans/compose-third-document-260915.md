## 1. 무엇을 말하는지 (한 장면)

지금은 DocuDog이 폴더를 보고 “이 파일은 계약서, 최신은 이쪽”까지는 알려 줌.  
사용자는 Cursor/Claude에서 **채팅으로** 그걸 읽음.

추가로 원하는 장면은 이럼:

1. 바탕화면에 흩어진 A.docx, B.hwp, C.pdf, A2_최종.pptx 를 **몇 개만** 고름.
2. “이걸로 임원 보고용 1페이지 요약 만들어” 또는 “후임 인수인계 목차 만들어”라고 말함.
3. DocuDog이 **새 파일**을 하나 만듦 (원본은 안 옮김, 이름도 안 바꿈).
4. 그 파일을 메일·공유폴더·프린터로 넘김.

기존 MCP 검색/컨텍스트 팩은 **채팅 안의 짧은 묶음**임.  
이 기능은 **디스크에 남는, 사람용 산출물**임. 둘은 대체 관계가 아님.

## 2. 사용성 검토 (넣을지 / 넣지 말지)

### 도움이 되는 이유

- **정리 노동이 아님.** 매일 태그·폴더를 맞추는 일이 아니라, 인수인계·주간보고처럼 **가끔 한 번** 하는 일임.
- **첨부 지옥을 줄임.** 지금 사람들은 같은 파일을 채팅에 다시 붙이거나, 직접 복붙해서 요약을 만듦. 이미 추출·요약·계보가 있는 PC에서 만드는 편이 맞음.
- **master-plan과 맞음.** “사내 무인 인수인계”는 플랜에 이미 있음. 다만 지금은 DNA 그래프를 **다른 PC에 주입**하는 큰 그림이고, 1차는 **한 PC에서 인수인계 문서를 뽑는 것**이 현실적임.
- **최신본 렌즈와 맞음.** `_v1` / `_최종`이 섞여 있어도, 사용자가 “이 과제 관련 파일들”만 고르면 lineage의 최신 힌트를 제3 문서에 박을 수 있음 (`260910-02`와 시너지).

### 도움이 안 되거나 위험한 이유

- **문서 브라우저 GUI**를 만들면 Notion/Obsidian 정리 피로를 재현함. 파일 트리·체크박스 앱은 이 제품이 아님 (`260910-D`).
- **모든 분류 결과를 위키 페이지로 자동 생성**하면 LLM-Wiki와 같아짐 (`260604-C` 보류). 사용자 **요청이 있을 때만** 한 파일을 씀.
- **워치 폴더에 결과물을 쓰면** 그 MD/HTML이 다시 분류 큐에 들어가 루프가 남. 기본 출력은 `%USERPROFILE%/.docudog/composed/` 처럼 **감시 밖**.
- **P1/P2 원문을 제3 문서에 풀면** 메일로 나가기 쉬운 파일이 됨. MCP와 같은 발췌 정책을 기본으로 두고, 민감 건은 제목·경로·한 줄만 또는 명시적 확인 후에만 본문 합성.
- **context_pack과 중복**처럼 보일 수 있음. 구분: pack = 에이전트용 짧은 마크다운 반환 / compose = 사용자가 지정한 템플릿으로 **파일 저장**. pack을 먼저 만들어 compose가 그 위에 파일을 쓰게 하는 순서가 자연스러움 (`260910-04`, `260805-02` 선행 권장, 필수는 아님).

### 결론

**조건부 채택.**  
입구는 MCP 도구 + CLI (`python main.py --compose …` 또는 `tools/compose_docs.py`). 웹/탐색기 GUI는 하지 않음.  
출력은 감시 밖 산출물 홈. 원본 불변. 포맷은 쉬운 것부터.

사용성 점수는 “가끔 쓰는 고가치 작업(인수인계·보고)”에서 큼. “매일 자동으로 새 문서를 쌓기”로 가면 점수가 떨어짐.

## 3. 기능 A — 선택 문서 기반 요약·보고서 (제3 문서)

### 사용자 입력

- **선택:** `file_id` 목록, 또는 절대 경로 목록, 또는 자연어(“Q3 견적 관련 최신 3개”). 자연어는 내부에서 search/resolve를 탄 뒤 **후보를 되묻고** 확정하는 편이 안전함. 1차는 명시적 경로/`file_id`만.
- **의도(instruction):** 자유 텍스트. 예: “임원용 10줄”, “표로 일정만”, “영문 bullet”.
- **템플릿(선택):** `brief` | `report` | `custom`. 없으면 instruction만.
- **출력 포맷:** 아래 사다리.
- **출력 경로(선택):** 없으면 `composed/YYYYMMDD-HHMM-{slug}.md`.

예시(개념, API 확정 아님):

```
python tools/compose_docs.py --ids id1,id2,id3 --intent "주간 이슈 한 장" --format md
```

MCP면 `docudog_compose(file_ids, intent, format)` 가 경로를 반환. **쓰기 MCP는 기본 읽기 전용 정책과 충돌**하므로, 1차는 **로컬 CLI만 쓰기**하고 MCP는 “초안 마크다운을 응답으로만 주고, 저장은 사용자가 저장”도 후보임. 구현 때 둘 중 하나를 고름:

| 옵션 | 장점 | 단점 |
|------|------|------|
| CLI만 파일 저장, MCP는 본문 반환 | 읽기 전용 MCP 유지 | 초보가 CLI를 못 씀 |
| MCP가 `.docudog/composed/`에만 저장 | Cursor에서 한 방 | 게이트웨이가 디스크에 씀. allowlist·토큰 필수 |

권장 1차: **로컬 프로세스 CLI 저장**. MCP는 `docudog_compose_preview`로 마크다운 문자열만 (P정책 적용). 트레이에 “마지막 preview를 composed 폴더에 저장”은 2차.  
파일 고르기는 CLI가 약함. 체크박스 UI가 필요하면 **문서 탐색기 앱이 아니라** 로컬 운영 페이지의 한 섹션으로 둠 — [local-operator-dashboard-260915.md](local-operator-dashboard-260915.md) 단계 3.

### 파이프라인 (작업 단위)

1. 선택 집합 resolve (경로 존재, state에 있으면 `file_id`·등급·요약·latest 힌트).
2. 미분류면 `--file`과 같은 추출만 하고, 분류까지 강제할지 플래그로 둠. 1차는 **이미 분류된 것만** (빠를수록 사용 가능).
3. 각 소스: 메타(경로, 날짜, P, 태그, 한 줄 요약) + 정책 통과 시 본문 발췌(길이 캡). LiteRT prefill 한도를 넘기지 않게 `litert_aux_max_user_chars` 계열과 맞춤.
4. 소스 N개를 한 프롬프트에 다 넣지 말고, **맵-리듀스:** 파일별 짧은 메모 → 합쳐서 최종 초안. 파일이 많으면 상한(예: 8개, 총 문자 예산).
5. 결과 MD 저장 + 선택적 HTML 동기(기존 reporter HTML 패턴 재사용 검토).
6. activity 로그에 `[compose]` 한 줄 (어떤 소스, 출력 경로). 원본 SHA는 건드리지 않음.

### 포맷 사다리 (쉬운 것 먼저)

| 순위 | 포맷 | 이유 | 의존 |
|------|------|------|------|
| 1 | **Markdown** | 이미 리포트·status가 MD. 에이전트·Obsidian·Git이 읽기 쉬움. 구현 최소. | 표준 라이브러리 + 기존 inference |
| 2 | **HTML** | status/mobile digest가 이미 MD 동반 HTML. 브라우저·메일 붙여넣기. | 기존 HTML 변환 유틸 재사용. Word가 아님 |
| 3 | **DOCX** | 사무실에서 “파일로 주세요”가 많음. | `python-docx` 신규 의존. 스타일·한글 폰트·표가 깨지기 쉬움. **2가 안정된 뒤** |
| 보류 | HWP | 생성은 추출보다 훨씬 어려움. 사용자가 HTML을 한글에서 여는 우회가 현실적 | 하지 않음 |
| 보류 | PDF 생성 | 인쇄용은 좋으나 레이아웃 공수 큼 | 하지 않음 |

DOC는 “개발이 쉬운 것”이 아님. 사용자가 DOC를 말해도 **MD → HTML → (나중) DOCX** 순이 맞음.  
워드가 꼭이면 2차에서 HTML을 Word가 열 수 있게 안내하거나, 얇은 DOCX(제목+본문 단락만, 복잡한 스타일 없음).

### 제3 문서에 넣을 최소 뼈대 (brief/report 공통)

- 생성 시각, 사용한 모델 백엔드 (분류 리포트와 같은 신뢰 주의).
- 소스 목록: 경로, 분류 시각 vs 파일 mtime (`260910-06` stale 플래그가 있으면 표시).
- 본문: instruction에 따른 요약/보고서.
- 면책: “원본을 대체하지 않음. P등급은 참고.”

A/B/C/A2 예시: 같은 과제의 초안·최종·첨부 PDF·후속 PPT처럼 **포맷이 달라도** extract 파이프가 있는 확장자만. 스캔 PDF·암호는 소스 목록에 “본문 없음”으로만 남김.

## 4. 기능 B — 인수인계 / OJT 팩

기능 A와 **같은 compose 엔진**, 다른 **고정 템플릿**.

### 왜 따로 적는지

인수인계는 요약 문장보다 **지도**가 필요함. 후임은 “한 줄 요약”만으로는 어디부터 읽어야 하는지 모름.  
master-plan의 “그래프를 다른 PC에 주입”은 크고, 당장 쓰는 형태는 **읽을 순서 + 파일 목록이 있는 MD 한 장**임.

### 고정 목차 (초안)

1. **개요 (OJT 한 장)**  
   - 이 묶음이 무슨 업무인지 (LLM, 소스 요약·태그·카테고리 기반).  
   - 지금 최신으로 보면 되는 파일 1~2개 (lineage `latest` / thread).  
   - 주의: P1이 섞이면 “민감 문서는 목록만, 내용 합성 안 함”.
2. **읽는 순서 (목차)**  
   - 권장 순서: 정책/계약 → 최신 산출물 → 참고 초안.  
   - 각 항목에 “왜 이 다음인지” 한 줄.  
   - 버전 그룹은 `_초안`을 본편에 넣지 않고 “이전 버전” 각주로.
3. **문서 목록**  
   - 표: 표시 이름, 경로(클릭 가능한 `file://` 는 HTML일 때만 검토, MD는 백틱 경로), 형식, P등급, 마지막 분류, stale 여부, 한 줄 요약.  
   - 같은 SHA 중복 경로는 한 줄로 합침 (`docudog_by_hash` 감각).
4. **공백 (있으면)**  
   - cadence 미작성, 추출 실패(스캔 PDF)는 “아직 없음/못 읽음”.

### 선택 UX

사용자가 파일을 고르는 게 1차.  
2차(선택): thread_id 또는 lineage 그룹 하나를 고르면 멤버를 후보로 채움. **자동으로 폴더 전체 덤프는 하지 않음** (노이즈·P1 혼입).

### 성공 기준 (사람이 느끼는 것)

후임이 이 파일만 열고, 표의 경로를 따라가면 **첫날 읽을 것**이 보임.  
DocuDog 채팅 히스토리를 넘겨주지 않아도 됨.

## 7. 설정 스케치 (구현 시 확정)

`compose_settings` 같은 블록을 나중에 넣음. 지금은 키 이름 고정 아님.

- `output_dir` (기본 artifact_home/composed)
- `max_sources`, `max_chars_per_source`
- `allow_p1_body` (기본 false)
- `formats_enabled`: `["md"]` 후 `html`, `docx`

Watch 설정에 composed 경로 exclude. artifact_home 아래면 이미 워치 루트와 분리된 경우가 많음 — 확인만 하면 됨.
